# diligent-sys

Raw `bindgen`-generated FFI bindings to the
[DiligentEngine](https://github.com/DiligentGraphics/DiligentEngine) (DiligentCore)
C API, with a `build.rs` that builds the native `DiligentCore` static library via CMake.

This is a plain bindings crate: **no runtime translation layer**. Everything
re-exported here is the raw `extern "C"` surface of Diligent — structs, typed
enums, constants, Vtbls and global entry functions.

## What you get

- `bindings` module (re-exported at crate root): all C API types from
  `Graphics/GraphicsEngine/interface/*.h` plus the D3D12 and Vulkan engine
  factory headers, generated by bindgen at build time into
  `OUT_DIR/bindings.rs`.
- `DiligentCore` native static library (Windows: Direct3D12 backend only),
  built by CMake into `OUT_DIR/diligent-build/` and linked into this crate.
- Entry points: `Diligent_GetEngineFactoryD3D12()` (Windows D3D12) and
  `Diligent_GetEngineFactoryVk()` (generated for the future Vulkan path).
  Interface methods are called through the generated `I<Interface>Vtbl`
  function-pointer fields. There are **no** standalone
  `I<Interface>_<Method>(This, ...)` functions: in the C headers those
  names are function-like macros (`CALL_IFACE_METHOD(...)`) that bindgen
  cannot emit. Each Vtbl nests one `I<Interface>Methods` struct per base
  interface in the inheritance chain, so a call looks like:

  ```text
  (*(*pFactory).pVtbl).EngineFactoryD3D12.CreateDeviceAndContextsD3D12
  ```

  (with `Diligent_GetEngineFactoryD3D12()` for `pFactory`; the method field
  is an `Option<unsafe extern "C" fn(...)>`, i.e. a nullable function
  pointer).

## Prerequisites (Windows)

- Rust (MSVC toolchain), CMake >= 3.20, a C/C++ compiler for MSVC (cl.exe),
  Ninja (optional — auto-detected via `where`), LLVM/clang with `libclang`
  (for bindgen), and the Windows SDK with `d3d12.h`.
- `third_party/DiligentEngine/` checkout next to the crate
  (`CARGO_MANIFEST_DIR/../../third_party/DiligentEngine`). Missing ThirdParty
  submodules are backfilled automatically from codeload.github.com tarballs,
  each recorded with URL + SHA-256 in
  `third_party/diligent-fetched.sha256` (see below).

## Build (Windows / D3D12 — verified)

```powershell
cargo build --manifest-path crates/diligent-sys/Cargo.toml
```

This runs, in order:

1. `ensure_submodules()` — for every submodule in `.gitmodules` whose
   directory is empty, fetch
   `https://codeload.github.com/DiligentGraphics/<repo>/tar.gz/<ref>`
   (`ref = refs/heads/master`, pin point in `codeload_ref()`), extract it in
   place, and record URL + SHA-256 in `third_party/diligent-fetched.sha256`.
2. `cmake -S third_party/DiligentEngine -B $OUT_DIR/diligent-build -G Ninja`
   with `-DCMAKE_BUILD_TYPE=Release`, `-DDILIGENT_NO_DIRECT3D11=ON`,
   `-DDILIGENT_NO_VULKAN=ON`, `-DDILIGENT_NO_OPENGL=ON`,
   `-DDILIGENT_NO_SUPER_RESOLUTION=ON`, `-DDILIGENT_NO_ARCHIVER=ON`,
   `-DDILIGENT_BUILD_TESTS=OFF`, `-DDILIGENT_BUILD_TOOLS=OFF`,
   `-DDILIGENT_BUILD_SAMPLES=OFF`, `-DDILIGENT_USE_OPENXR=OFF`,
   `-DDILIGENT_INSTALL_CORE=ON`.
3. `cmake --build <build dir> --target DiligentCore-static` (combined static
   library only — no shared DLLs).
4. `bindgen` over the C API headers; `bindings.rs` written to `OUT_DIR`.

MSVC tools / Windows SDK discovery can be overridden with
`DILIGENT_MSVC_TOOLS_DIR` (the `VC/Tools/MSVC/<ver>` directory) and
`DILIGENT_WINDOWS_KITS_DIR` (the `Windows Kits/10` directory). The cmake
executable can be overridden with `DILIGENT_CMAKE`, ninja with `DILIGENT_NINJA`.

### Degradation path: bindgen only

If the native build is blocked (missing toolchain, broken submodule chain,
offline), the bindgen half can be verified independently:

```powershell
$env:DILIGENT_SKIP_CMAKE=1
cargo build --manifest-path crates/diligent-sys/Cargo.toml
```

The crate compiles and produces `bindings.rs`, but the final link does **not**
include `DiligentCore` (the link-fuse that pins the static library is gated
behind the `diligent_native_linked` cfg, set only when cmake succeeded).

## Build templates (future work — not implemented, not verified)

**The implementation is currently Windows/D3D12-only.** `build.rs` performs
no per-OS backend selection: the native-build path calls
`find_windows_msvc()` unconditionally (`build.rs`), so on Linux/Android it
fails before cmake runs. The sections below are *templates for future work*
only — no claim is made that any of them works today.

### Linux / Vulkan (future-work template)

```sh
# Not implemented: would require a Linux cmake path (no MSVC discovery),
# -DDILIGENT_NO_VULKAN left off, Vulkan SDK headers, and Linux clang
# defines in platform_clang_defines() (see build.rs for the sketch).
cargo build --manifest-path crates/diligent-sys/Cargo.toml
```

`platform_clang_defines()` in `build.rs` documents the Linux/Vulkan define
set (`PLATFORM_LINUX=1`, `VULKAN_SUPPORTED=1`, `D3D12_SUPPORTED=0`,
`GL_SUPPORTED=1`, `GLES_SUPPORTED=0`, `DILIGENT_VK_SHARED=0`) plus the
clang include for `ThirdParty/Vulkan-Headers/include` — the intended shape
of the future Linux path, not a working configuration.

### Android NDK (future-work template, cross)

```sh
# Not implemented: same Linux-blocking issue plus an NDK sysroot; the
# template below shows the intended shape only.
export ANDROID_NDK_HOME=/path/to/ndk
export CC=$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/bin/aarch64-linux-android34-clang
export CXX=${CC%clang}++
cargo build --target aarch64-linux-android --manifest-path crates/diligent-sys/Cargo.toml
```

The `platform_clang_defines()` function in `build.rs` documents the Android
platform defines (`PLATFORM_ANDROID=1`, `VULKAN_SUPPORTED=1`,
`GLES_SUPPORTED=1`) needed for a clean bindgen run; this path has **not**
been implemented or executed, and would need NDK-sysroot include paths
added.

## Submodule backfill procedure

DiligentEngine pins ThirdParty dependencies as git submodules. In a checkout
without git metadata (or when `git submodule update` is unavailable), empty
submodule directories are populated from codeload tarballs:

```
https://codeload.github.com/DiligentGraphics/<repo>/tar.gz/refs/heads/master
```

`build.rs` reads `.gitmodules`, and for every submodule whose directory is
empty downloads the tarball and extracts it in place. The only download
channel used is `codeload.github.com`.

Every fetched tarball is recorded with its **URL and SHA-256** in the
manifest `third_party/diligent-fetched.sha256` (format:
`<sha256>  <repo>  <url>`), per the reproducibility requirement (§2.1b).
Verification on reuse: a usable checkout whose manifest entry is present is
never refetched; a usable checkout without an entry (backfilled before
checksum recording) is left as-is with a warning; an empty directory is
always refetched. Current record (Windows/D3D12 verified build):

| repo | url | sha256 |
|------|-----|--------|
| SPIRV-Cross | `https://codeload.github.com/DiligentGraphics/SPIRV-Cross/tar.gz/refs/heads/master` | `53fbc951fc212e0568c4d73b175dad5f8ec803abc01afad2fe0ab0d8f54ba40d` |

Repos fetched this way are on `master` (not the pinned commit); the
`codeload_ref()` function in `build.rs` is the pin point — set it to a
concrete commit SHA (`.../tar.gz/<sha>`) once a verified-good commit is
recorded for a repo. To force a backfill of a specific submodule, empty its
directory (e.g. `Remove-Item -Recurse ThirdParty/SPIRV-Cross/*`) and
rebuild; the new URL+SHA-256 replaces the old manifest entry.

## Layout

- `build.rs` — cmake build + toolchain discovery + submodule backfill + bindgen
- `src/lib.rs` — includes `OUT_DIR/bindings.rs`; re-exports the whole FFI surface
- `Cargo.toml` — `crate-type = ["staticlib", "cdylib", "rlib"]`; standalone
  `[workspace]` (the repo root workspace currently conflicts with
  `tools/m0_shader_smoke`'s own workspace; build with `--manifest-path` until
  that is resolved)
